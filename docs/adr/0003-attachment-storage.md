# ADR-0003. Выбор хранилища для пользовательских вложений

- Статус: принято
- Дата: 2026-11-18

## Контекст

Веб-приложению TimeCapsule требуется надёжное и масштабируемое хранилище для файлов, которые пользователи прикрепляют к капсулам времени. В текущей архитектуре сервер приложения (`timecapsule-dev-app`) работает на одном экземпляре EC2, однако в дальнейшем планируется переход к отказоустойчивой схеме с несколькими серверами за балансировщиком нагрузки (ALB). Решение должно исключать потерю файлов при пересоздании инстансов EC2, обеспечивать приватный доступ только авторизованным владельцам капсул и не требовать ручного управления дисковым пространством.

## Решение

Храним все пользовательские вложения в **объектном хранилище Amazon S3** (бакет `timecapsule-dev-uploads-risovoepole`, префикс `uploads/`).

- Доступ приложения к бакету осуществляется через AWS SDK без статических ключей в `.env` — с помощью **IAM-роли** (`timecapsule-dev-app-role`), назначенной инстансу EC2, с политикой минимальных привилегий (`timecapsule-dev-app-s3`: `GetObject`, `PutObject`, `DeleteObject` только для `uploads/*`).
- На уровне бакета включён полный запрет публичного доступа (`Block Public Access`), настроено шифрование по умолчанию (SSE-S3) и добавлена `Bucket Policy`, отклоняющая любые запросы без HTTPS (`aws:SecureTransport = false`).
- В базе данных PostgreSQL хранятся только метаданные и случайное имя ключа объекта.

## Рассмотренные альтернативы

- **Локальный диск EBS сервера приложения (`storage/uploads`)**:
  - Отказались, так как локальный EBS-том жёстко привязан к конкретному инстансу EC2 в одной зоне доступности. При удалении сервера (`Terminate`, `DeleteOnTermination = true`) все пользовательские файлы безвозвратно пропадут. Кроме того, при добавлении второго сервера приложения за балансировщиком нагрузки файлы, загруженные на один инстанс, окажутся недоступны при попадании запроса на другой.
- **Общая сетевая файловая система Amazon EFS (Elastic File System)**:
  - Отказались как от избыточного и более дорогого решения для нашей задачи. EFS оправдан, когда нескольким инстансам EC2 требуется полноценная POSIX-совместимая файловая система с монтированием по NFS и одновременной записью в общие директории. Однако хранение в EFS стоит значительно дороже S3 (~$0.30/ГБ в месяц против ~$0.023/ГБ в S3 Standard), требует настройки Mount Targets и Security Groups в подсетях, а также по-прежнему заставляет проксировать весь трафик скачивания через PHP-FPM и Nginx.

## Последствия

- **Плюсы**:
  - Высокая надёжность и долговечность хранения (99.999999999% durability) с автоматической репликацией между несколькими зонами доступности внутри региона `eu-central-1`.
  - Разгрузка веб-сервера: отдача крупных файлов происходит напрямую из S3 в браузер пользователя, не занимая воркеры PHP-FPM и сетевой канал `app-server`.
  - Отсутствие необходимости заранее выделять и вручную расширять объём диска — оплата производится строго по факту занятого места.
- **Минусы и риски**:
  - Зависимость от сетевой доступности S3 API и необходимость корректно управлять правами IAM и политиками бакета.
  - В локальной среде разработки без доступа к AWS требуется либо отдельный dev-бакет, либо совместимый эмулятор (например, MinIO).
- **Получение файлов пользователем и ограничение срока действия ссылки**:
  - При запросе на просмотр или скачивание вложения приложение сначала проверяет права текущего пользователя на доступ к капсуле в PostgreSQL. После успешной проверки PHP-бэкенд генерирует через AWS SDK временную подписанную ссылку (**Presigned URL** на операцию `GetObject` с нужными заголовками `ResponseContentType` и `ResponseContentDisposition`) и возвращает браузеру редирект `302 Found`. Браузер скачивает файл напрямую из S3 по HTTPS.
  - Срок действия подписанной ссылки ограничивается двумя факторами: явно заданным параметром времени жизни в самой подписи (`+5 minutes` / `X-Amz-Expires=300`, после чего S3 отклоняет запрос с ошибкой `403 AccessDenied`) и сроком жизни временных учётных данных IAM-роли EC2 (полученных через IMDSv2) — если токен сессии роли истекает раньше, подпись также становится недействительной.
- **Защита от случайного удаления и контроль роста стоимости**:
  - От случайного удаления или перезаписи объектов защищает включённое **версионирование бакета (S3 Versioning)**: при вызове `DeleteObject` объект не стирается физически, а помечается маркером удаления (`Delete Marker`), и любую предыдущую версию можно восстановить. Дополнительную защиту обеспечивает политика IAM, запрещающая удаление самого бакета и ограничивающая операции только префиксом `uploads/*`.
  - Рост стоимости хранения ограничивается настройкой **правил жизненного цикла (S3 Lifecycle Rules)** — например, автоматическим переводом редко запрашиваемых объектов или старых версий в более дешёвые классы хранения (`S3 Standard-IA` / `Glacier`) и окончательным удалением неактуальных (неактивных) версий по истечении заданного срока (например, через 30–90 дней), а также настройкой уведомлений о бюджете в AWS Budgets.
- **Масштабирование до нескольких серверов приложения за балансировщиком нагрузки (ALB)**:
  - При добавлении новых экземпляров `app-server` за балансировщиком нагрузки архитектура хранения **не потребует никаких изменений**: все веб-серверы остаются полностью безсостоятельными (*stateless*) в отношении файлов. Каждый инстанс в Auto Scaling Group получает ту же IAM-роль (`timecapsule-dev-app-role`) и работает с единым бакетом S3, поэтому любой сервер может обработать загрузку файла, а пользователь гарантированно получит доступ к своему вложению независимо от того, на какой именно экземпляр ALB направит его следующий запрос.
